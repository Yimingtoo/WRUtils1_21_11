### P1. `snapshot` 未先加载区块（高）——改为“未加载拒绝执行”

- **方案原文**（473-474）：「`forceChunks()` 提到 `applyCleanup()` **之前**。快照要读方块状态，
  未加载的区块读出来是空气，不先加载就会把整片区域记成“本来什么都没有”。」
- **原实现**：`WorldPrep.prepare()` 仅在 `forceChunks=true` 时加载，而方案 135 明确默认 `false`。
- **最终决策（2026-10-17）**：`snapshot` + `forceChunks=false` 时**不再隐式加载**，
  启动前检查测试涉及的区块；有未加载的直接拒绝（不加载、不触发生成）。
  `forceChunks=true` 仍显式加载；`none` / `clear_input` 不变。
- **历史**：曾先实现为“snapshot 无条件强制加载”，随后按用户决策改为上述拒绝语义。
- **验证**：见 [Phase 7 评审修复验证手册](Phase7评审修复验证手册.md) §13–§16
  （§2–§6 是旧行为的历史记录）。
- **状态**：工作区已改，`typecheck` 通过；**游戏内验证通过（2026-10-17，§13–§16）**。
- **配套缺口**：编辑器目前没有 `forceChunks` 的 UI 入口（方案「Phase 8 候选」已列出
  `AreaSpec` 的 `forceChunks`/`clearEntities`/`gameRules`）。新拒绝信息会提示用户改 JSON，
  在补 UI 之前这是唯一启用方式。

### P2. 多可写区仍按包围盒处理（高）——已修复

### P3. 窗口断言异常不走 `ABORTED`（中）

- **方案原文**（141）：「超时（超过 `timeoutTicks`）或异常 → `ABORTED`，仍走 `FINISHING` 清理」。
- **证据（已核实）**：`TestRun.tick` 的 `try/catch` 只包住步骤循环（约 246-250），
  本 tick 末尾的 `checkPendingAsserts()`（约 255）在 `try` 之外；窗口断言抛 `RuntimeException`
  会冒泡出 `END_WORLD_TICK`，run 卡在 `RUNNING` 或世界 tick 报错。
- **建议**：把 `checkPendingAsserts()` 纳入同一个 `try`，或在方法内自行捕获并
  `finish(ABORTED)`；异常信息应进入报告（不能静默吞掉）。
- **处理（2026-10-17）**：`checkPendingAsserts()` 已纳入步骤循环的同一个 `try`，
  异常走 `finish(ABORTED)`。`typecheck` 通过；异常路径难以在游戏内构造，按代码级验证。

### P6. 失败 `step#` 含 `setup` 偏移（中）

- **方案原文**（121）：「模型层保留 `setup` 与 `steps` 两个独立列表……引擎内部仍是单一时间轴」；
  （182-183）失败信息示例 `step#N`。
- **证据（已核实）**：`TestRun.flatten` 把 `setup` 转成 `PlaceStep` 放在 `steps` 前面；
  `TestScheduler` 的 `index` 是合并后列表下标；`Failure.describe` 直接打印该下标。
  因此报告里的 `step#` 比用户可见 `steps` 下标大 `setup.size()`。
  （进度 HUD 的「第几步 / 共几步」也含 setup，需确认是否同为预期语义。）
- **建议**：引擎内部可继续用单一时间轴，但 `Failure` / 进度展示应使用**原始 steps 下标**；
  可在 `flatten` 时记录来源与原始索引，或统一在展示层减 `setup.size()`。
  需同时决定：setup 步骤失败时 `step#` 显示什么（建议显示 `setup#N` 或 `setup`）。
- **处理（2026-10-17）**：报告与窗口断言的 `step#` 改为 `scheduled.index() - setup.size()`，
  即用户可见的 steps 下标。setup 只有 place、没有 assert，place 失败原本就不显示 `step#`，
  因此无需额外分支。`typecheck` 通过；已验证通过（§19，报告为 `step#1`）。
